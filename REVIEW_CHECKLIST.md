# Контрольний список перевірки коду

Чекліст використовується під час ручного огляду змін у проєкті ClinicReception перед їх прийняттям.

## 1. Іменування та зрозумілість

- [ ] Чи зрозуміле призначення методу з його назви без читання всього тіла?
- [ ] Чи зрозумілі назви змінних і параметрів з погляду предметної області?
- [ ] Чи не використовуються незрозумілі скорочення в назвах класів і методів?

## 2. Обсяг і структура змін

- [ ] Чи виконує кожен змінений метод одну основну задачу?
- [ ] Чи не містить клас зайвої відповідальності, яка належить іншому класу?
- [ ] Чи не дублюється однакова логіка в різних частинах програми?

## 3. Дані та логіка

- [ ] Чи немає магічних чисел або рядків, які краще винести в окремі константи?
- [ ] Чи правильно обрані типи даних для грошей, дат і часових інтервалів?
- [ ] Чи правильно перевіряються дати запису пацієнта та тривалість прийому?
- [ ] Чи враховані можливі граничні значення, наприклад від'ємна вартість або дата в минулому?


## 4. Обробка помилок

- [ ] Чи передбачено обробку некоректних даних, які вводить користувач?
- [ ] Чи містять повідомлення про помилки зрозуміле пояснення для користувача?
- [ ] Чи не приховуються винятки без обґрунтованої причини?

## 5. Документація та тести

- [ ] Чи додано XML-коментарі до нових публічних класів і методів, якщо вони потрібні для розуміння їх використання?
- [ ] Чи є тести для кожної нової гілки важливої бізнес-логіки?
- [ ] Чи перевіряють тести не тільки правильний результат, а й можливі помилкові ситуації?

## 6. Прибирання коду

- [ ] Чи не залишився закоментований код, який більше не використовується?
- [ ] Чи не залишилися TODO-коментарі без відповідного запису в плані або журналі завдань?

## 7. Культура огляду

1. Зауваження потрібно формулювати до коду, а не до автора. Необхідно пояснювати, що саме потрібно виправити, не оцінюючи особисті якості розробника.
2. Кожне зауваження має містити конкретну дію. Наприклад: «Винесіть значення 0.9 в окрему константу» замість «Незрозуміло».
